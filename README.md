# Igniter（`local.igniter`）· PI-Desktop 插件

按计划给一个模型"点火"：在每天指定的时段内，每隔一段时间用它发一次最小补全，让上游的额度窗口保持活跃，
顺带可以每次结果推一条 Bark 通知到手机。

所有请求都走 PI-Desktop 宿主的 `agent.complete`——**插件永远拿不到你的 API 密钥**，也不决定请求发往哪个地址。
唯一的网络访问是你自己填的 Bark 地址，不填就完全不联网。

调度骨架参考 [cpa-plugin-lamplighter](https://github.com/PosvdM/cpa-plugin-lamplighter)，
但去掉了所有依赖 5 小时额度窗口的部分：反代不返回窗口信息，所以这里只需要"时段 + 间隔 + 延迟 + 模型"。

---

## 快速开始

1. **安装**：在 PI-Desktop 插件页安装 `local.igniter-0.1.0.piplug`
   （自己打包的步骤见[开发](#开发)）。
2. **打开面板**：命令面板执行 `Igniter: Open Panel`。
3. **选模型**：在「模型」下拉里选 PI-Desktop 已配置好的提供商与模型，点「保存」。
4. 想确认配置是否正确，点「立即激活一次」——它不受时段和熔断限制。

出厂默认是 03:00–19:00、每 300 分钟（5 小时）一次、每个边界之后延迟 60 秒，
也就是 03:01、08:01、13:01、18:01 各发一次。选好模型后这套默认就已经能用，需要时再改。

> Bark 推送、免打扰都是可选的，不配置不启用。

## 行为

### 时段与触发网格

- 时段：`startHour` 到 `endHour`（小时，`endHour` 可取 24）。`start < end` 是普通时段，
  `start > end` 视为跨夜，`start === end` 视为全天（00:00 到起始小时之间属于前一天开始的那个窗口）。
- 触发网格：以**当天窗口起点**为锚，`起点 + 延迟 + k × 间隔`。用绝对时间计算，不累加，所以不会漂移。
  例：起点 03:00、间隔 300 分钟、延迟 60 秒 → 03:01、08:01、13:01、18:01。
- 网格点落在结束时间或之后时丢弃，下次触发改为**次日窗口的第一个点**，永远不会发生在时段之外。
- 错过的网格点（插件停用、机器休眠、刚启用）会立即补一次，而不是顺延整整一个间隔。
- 触发内容：`pi.agent.complete({ modelKey, messages: [{ role: "user", content: "OK" }], thinkingLevel: "off" })`。

### 失败保护

分两类，区别在于"值不值得再试"：

**普通失败**（模型不存在、401/403、5xx、网络错误）

- 按 1×/3×/9× 退避重试（上限为当前间隔）。
- 连续 3 次失败后熔断，暂停到下一次 `startHour`，并发一次系统通知。
- 成功即清空失败计数、关闭熔断。
- 熔断到期后计数归零，新的一天重新给满次数。

**被限流（429）**

上游限流不是"配置坏了"，直接按普通失败处理的话第 3 次就把整天停掉。所以它有自己的一套节奏：

| 项 | 普通失败 | 被限流（429） |
| --- | --- | --- |
| 重试退避 | 1、3、9 分钟（上限＝当前间隔） | 5、10、20、40、60 分钟（上限 60 分钟） |
| 尊重 `Retry-After` | 否 | 是：`retry-after`（秒）或 `retry-after-ms`（毫秒），夹在 1 秒–60 分钟之间 |
| 连续几次后熔断 | 3 | 6 |
| 熔断后 | 暂停到下一次 `startHour` | 同左（6 次累计约 2 小时 15 分，持续被限流才会走到） |
| Bark | `⚠️ 点火失败`，`timeSensitive` | `⏳ 被限流`，`passive`（不响铃，避免每次重试都打扰） |
| 面板「上次结果」 | 显示「失败」 | 显示「被限流」 |

识别依据是 `status === 429`、`code` 里含 `RATE_LIMIT`，或 message 里出现 `429` / `rate limit` / `too many requests`
（宿主自己的每分钟 8 次配额 `RATE_LIMITED` 也算在内）。宿主的包装形式形如：

```
429: custom API error (429): {"code":"upstream_rate_limited","message":"Upstream rate limit exceeded."}
```

限流期间的等待只影响重试时刻，窗口网格本身不变；等过了 `retryAt` 仍在窗口内就补跑，已经出窗口就等下一个窗口。

### 手动点火

面板上的「立即激活一次」绕过时段与熔断，用来确认配置是否正确：

- **成功**会清空失败计数并关闭熔断——说明配置已经好了。
- **失败只记录、只提示**：不计入失败次数、不触发熔断、不安排重试，下一次自动点火的时间也不变。
  调试配置时连按几次，不会把当天的自动点火停掉。
- 这时的 Bark 推送标题带「（手动）」，正文不写"N 分钟后重试"（因为确实没安排重试），级别 `active`（被限流则 `passive`）。
- 没选模型时它什么都不做，也不计失败，只提示「未选择模型」。

### 免打扰

默认**不启用**，不设置就一切照旧。启用后，落在该时段内的通知不发送：

- **被拦住的**：Bark 推送、熔断时的系统通知。记录里的 `bark` 字段会写成 `quiet`，
  这样"被安静掉"和"推送失败"能区分开。
- **不受影响的**：面板内的 Toast（不打扰任何人，开着面板时仍能看到发生了什么）、
  「测试 Bark 推送」按钮（你主动按的，就该送达）、点火本身（该点火还点火，只是不通知）。
- 时段可以跨夜：开始 23、结束 7 表示 23:00–07:00；开始小于结束表示同一天内（如 13–15）。
- 起止相同视为**不启用**，而不是"全天静音"——静默一整天比设置不生效更容易让人踩坑。
- 只按本机本地时间判断，和调度时段用的是同一套小时语义（`end=24` 表示到午夜）。
- 免打扰不会推迟或跳过点火，只影响通知。

### Bark 推送

配置了 `barkUrl` 后，每次自动点火都会推一条：

| 场景 | 标题 | 正文 | level |
| --- | --- | --- | --- |
| 成功 | `Igniter ✅ 点火成功` | `模型名 · 耗时` | `active` |
| 失败（会重试） | `Igniter ⚠️ 点火失败` | `模型名 · N 分钟/秒后重试 · 错误` | `timeSensitive` |
| 熔断 | `Igniter 🔴 已暂停` | `连续 N 次失败，暂停到 MM/DD HH:mm · 错误` | `timeSensitive` |
| 被限流（429） | `Igniter ⏳ 被限流` | `模型名 · N 分钟后重试 · 错误` | `passive` |
| 手动点火失败 | `Igniter ⚠️ 点火失败（手动）` | `模型名 · 错误` | `active` / `passive` |

- 模型名即 `providerId/modelId`；当 providerId 是不透明的 UUID 时只显示 `modelId`。
  错误文本里的 URL 一律只保留来源（`https://host/[redacted]`），避免密钥写进记录或推送。
- 地址填 `https://api.day.app/<key>` 即可，插件自动补 `/<标题>/<正文>?group=Igniter&level=…`；
  也可以填含 `{title}`、`{body}` 的完整模板（自建服务器、带 token 的路径都能用）。
- 标题和正文按 RFC 3986 非保留字符全百分号编码，中文和 emoji 不会被截断。
- **推送失败不影响点火结果**：Bark 单独超时 8 秒，失败只记一条 `warn` 日志并写进记录的 `bark` 字段，
  不计入失败次数、不触发熔断。HTTP 状态码非 2xx 或返回 JSON 的 `code != 200` 都算推送失败。
- 点火记录**先落盘、再推送**：Bark 很慢或无响应时记录也不会丢，推送结果随后补写进同一条记录。
- 设置区的「测试 Bark 推送」会先用输入框里的地址保存一次，再立即推一条测试消息并回报结果；
  它不受免打扰影响。

### 面板

- 顶部状态：运行中 / 已停用 / 未选择模型 / 时段外 / 已暂停 / 即将触发 / 正在点火。
- 「下次触发」带倒计时和进度条。进度条按**这次等待本身的长度**计算：退避期间按退避时长，平时按间隔。
- 「上次结果」区分成功、失败、被限流，鼠标悬停可看完整错误。
- 退避期间会写明具体重试时刻（如「第 2 次失败，将于 10:05 重试」），被限流则写「第 N 次被限流」。
- 「最近记录」保留 50 条，每行标出：被限流、手动、推送状态（「免打扰未推送」/「推送失败」；成功送达不额外标注）。
- 中英双语，跟随宿主主题。

## 配置

没有 `contributes.settings`，配置由面板自己管理，存在插件数据目录的 `state.json`
（`pi.plugin.getDataPath()`，宿主所有，`fs` API 也够不到）。

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 是否按计划自动触发 |
| `startHour` | `3` | 时段起点（0–23） |
| `endHour` | `19` | 时段终点（0–24） |
| `intervalMinutes` | `300` | 间隔分钟，即节奏（1–1440）；5 小时＝`300` |
| `delaySeconds` | `60` | 每个边界之后的延迟秒数（0–3600） |
| `modelKey` | 空 | `providerId/modelId`，来自 `pi.models.list()`；首次使用必须选 |
| `barkUrl` | 空 | Bark 推送地址，必须以 `http://` 或 `https://` 开头，否则面板保存时会被拒绝；留空＝不推送 |
| `notifyOnCircuit` | `true` | 熔断时是否发**系统通知**；面板内的 Toast 不受这个开关影响，始终提示 |
| `quietEnabled` | `false` | 是否启用免打扰时段 |
| `quietStartHour` | `23` | 免打扰起点（0–23），仅在启用后生效 |
| `quietEndHour` | `7` | 免打扰终点（0–24），可跨夜 |

状态文件里的运行时字段（最近结果、失败计数、熔断与重试时刻、最近 50 条记录）在读取时会逐项校验类型，
被手改坏或提前版本格式不一致时回退到安全值。面板的「清空记录」会重置失败计数和熔断。

## 权限与隐私

| 权限 | 风险 | 用途 |
| --- | --- | --- |
| `ui.panel` | 低 | 配置与状态面板 |
| `notify` | 低 | 熔断提示（面板 Toast 始终显示 + 可关闭的系统通知） |
| `background.service` | 中 | 常驻调度 service |
| `models.list` | 中 | 模型下拉 |
| `agent.complete` | 高 | 发那一次最小补全 |
| `net.fetch` | 高 | 调 Bark 推送接口 |
| `net.anyHost` | 高 | Bark 地址由你在面板里填，manifest 无法预先写死域名 |

- **不申请任何 `fs` 权限**；API 密钥不出宿主进程（插件进程按宿主设计也拿不到环境变量）。
- 网络只用于你填写的 Bark 地址；没配 `barkUrl` 时插件完全不发网络请求。
- 配置与历史只存在插件自己的数据目录里。

> `net.fetch` / `net.anyHost` 属于权限放宽，宿主不允许**热重载**时扩权：升级时如果被拒，
> 在插件页**卸载后重新安装**即可，权限在安装时一次性授予。

## 宿主约束（设计上限，不是可调参数）

- `agent.complete` 每插件**每分钟最多 8 次**，超出返回 `RATE_LIMITED` 并计入失败，所以间隔最小 1 分钟。
- 单次 `agent.complete` 超时 90 秒；同一时刻只允许一个 in-flight，慢响应不会打乱节奏。
- 调度 tick 为 30 秒，所以实际触发时刻在到期后 0–30 秒内。
- `onLoad` 须在 15 秒内完成，其他钩子 5 秒内。

## 已知限制

- 失败计数按"连续失败"计，但不会在跨窗口时自动清零：前一天最后一次失败会带到次日，
  因此次日可能比"连续 3 次"更早熔断（熔断本身到期后会清零）。
- Bark 模板里如果已经写了 `level=`，插件仍会再追加一个，实际以服务器解析到的最后一个为准。
- 时段与免打扰都按本机本地时间判断；**夏令时切换当天**的实际触发时刻没有做专门测试。
- 同一时刻只跑一次点火：上一次还没结束（最多 90 秒）时，到期的或手动的点火会被跳过并记为 `in-flight`。

## 开发

### 目录

```
manifest.json                  插件清单（id: local.igniter），仓库根目录是唯一来源
package.json                   开发脚本与版本号（只用于开发，不进入插件包）
README.md                      本文件（同时打进插件包）
LICENSE                        MIT 许可证（同时打进插件包）
src/main.js                    插件进程：调度网格、退避熔断、状态持久化、面板 RPC
src/renderer/index.html        面板：配置表单、倒计时、上次结果、最近记录
scripts/build.js               组装 dist/local.igniter/，只放运行时需要的文件
test/scheduling.test.js        时段、网格、到期计算、配置/状态校验、失败分类与限流退避、免打扰、进度条时长（83 项）
test/host.test.js              假宿主集成：点火、熔断、429 限流、免打扰、手动与自动的区分、Bark 推送、出厂默认值（49 项）
test/panel.test.js             面板文案与脚本检查：字典函数必须被调用，脚本必须能编译（17 项）
test/panel.integration.test.js 面板↔插件往返：表单回填、保存落盘、Bark 测试推送、模型显示名、记录行、退避提示、进度条（22 项）
test/manifest.test.js          先构建，再对 dist/local.igniter 做 manifest 与打包内容校验
dist/local.igniter/            构建产物（不入库）：manifest.json、README.md、LICENSE、main.js、renderer/index.html
```

`manifest.json` 里的 `main`（`main.js`）和 `ui.panel`（`renderer/index.html`）是**相对 `dist/local.igniter/`**
的路径，不是相对仓库根目录。

### 构建、校验与打包

```bash
npm run build      # -> dist/local.igniter/
npm test           # 五组测试；最后一组会重新构建并校验打包内容
npm run check      # 只跑 manifest / 打包内容校验
```

然后在 PI-Desktop 里对 **`dist/local.igniter`**（不是仓库根目录）依次执行：

1. `PluginCheck`：校验清单、入口、权限。
2. `PluginPack`：生成 `dist/local.igniter-<version>.piplug`，在插件页安装。

注意：`PluginCheck` / `PluginPack` 只接受**当前打开项目内的相对路径**，所以要先把本目录作为项目打开。
不要对仓库根目录打包：安装器会把 `test/`、`scripts/`、`package.json` 一并打进去。

`test/manifest.test.js` 是离线版的同类校验（自带宿主权限白名单），并额外保证：包内容恰好是
`scripts/build.js` 里列出的那几个运行时文件，没有 `test/`、`src/`、`package.json`，
且包里的 `manifest.json` 与仓库根的一致。

### 版本

| 项 | 值 |
| --- | --- |
| 插件版本 | `0.1.0`（`manifest.json` 与 `package.json` 必须一致，`npm run build` 与 `npm test` 都会校验） |
| 清单格式 | `schemaVersion: 1` |
| 宿主要求 | 清单 `engines.piDesktop: ">=0.2.0"` 指 **PI-Desktop 宿主版本**，不是插件版本；本地验证用的是 PI-Desktop 0.21.0 |
| Node | `>=22`（仅开发与测试需要，运行时由宿主提供） |

发版前同时修改 `manifest.json` 和 `package.json` 的 `version`，再重新构建、打包。

#### 0.1.0 — 首次发布

- 时段 + 间隔 + 延迟的调度网格；以窗口起点为锚、用绝对时间计算，不漂移；错过的点自动补跑。

- **手动点火与自动调度的后果分离**：手动成功会清掉失败与熔断，手动失败只记录，不影响自动点火。

- Bark 推送成功 / 失败 / 熔断 / 限流各一种标题与级别；推送失败不影响点火结果；
  点火记录先落盘再推送。
- 配置与状态校验：Bark 地址必须是 `http(s)://`；状态文件字段逐项校验；没选模型时不会发请求。
- 错误文本里的 URL 只保留来源，密钥不会写进记录或推送。
